How a product goes live in PIM

A storyboard of the product data work behind an online store, from the request to release. Each step shows what happens, with an example, and what my part was.

Where
Apple, as a contract Content Specialist
Scale
Up to 1,000 product parts a month in 88 countries
My role
Product records, assortment, purchase rules, release
Tools
PIM, XML product files, ticketing, staging

The examples use a made-up brand, Northwind. Apple’s own data and setup stay private. The steps are the ones I followed.

  1. Step 1 · The request

    It starts with a ticket

    Requests came in from marketing, content, localization and publishing teams. Each one listed the parts to set up, where they would be sold and when.

  2. Step 2 · Parent and children

    A product is a family

    In PIM, a parent record holds what all versions share. Each child record is one sellable variant, by color or size, with its own part number.

    My partSetting up parent and child records, variant SKUs, product codes, colors and sizes.
    • Arc Pro Caseparent
    • NW412 · Sandchild
    • NW413 · Midnightchild
    • NW414 · Sagechild
  3. Step 3 · The fields

    Every field has to agree

    Each child has a part number, part name, display name, market and segment, and they all have to say the same thing. A display name that says one color while the part name says another is a wrong product on the page.

    My partChecking display names against part names for every SKU, then checking the rest of the file for the same mistake.
    Child recordNW413

    • Part nameArc Pro Case – Midnight
    • Display nameArc Pro Case, Midnight

    • SegmentConsumer
    Catch · NW413 · combined file
    FoundDisplay name said Sand, part name said Midnight.
    FixedDisplay name corrected, then every other part in the file checked for the same mismatch.

  5. Step 5 · The file

    Narrow the file to the request

    Product data came in XML files. I filtered and combined them down to the part numbers in each request, keeping each parent with its children so the family stayed whole.

    My partFiltering and combining XML product files, and confirming every requested part number was in the file.
    <!-- kept: parent and its requested children -->
<product id="arc-pro-case">
  <part number="NW412" color="Sand"/>
  <part number="NW413" color="Midnight"/>
  <part number="NW414" color="Sage"/>
</product>

    Every part number in the request is in the file, and none are missing their parent.

  6. Step 6 · 88 countries

    Translations and staging

    Product content was translated for each market, then every page was previewed in staging before go-live.

    My partCoordinating translation for 88 countries and checking content in staging.
    Before releasechecklist
    • Every requested part number is in the file
    • Display names match part names for every SKU
    • Country and segment assortment matches the request
    • Purchase rules set
    • Pages previewed in staging
  7. Step 7 · Release

    Publish, then report

    Once the checks passed, the parts were published on localized product pages. Status went back to the team in the daily stand-up.

    My partPublishing up to 1,000 product parts a month and raising blockers in stand-ups.

Where it carries over

Any online store runs on product data like this: parent and child records, variants, assortments and rules. Checking every request against the data before release is what keeps the right product in front of the right customer.
